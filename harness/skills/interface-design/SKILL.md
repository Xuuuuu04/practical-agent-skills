# 界面设计

让第一次使用的人能判断自己在哪里、下一步做什么、操作后发生了什么。先解决任务与页面组织，再处理视觉细节；界面简洁与好看都服务于实际使用。

已有项目先读业务说明、现有页面和公共组件，沿用明确的品牌、平台和设计约定。发现原有安排妨碍使用，说明具体操作及影响，提出范围合适的改法。普通文字、间距或样式修复只用相关规则，不扩大成全站设计。

## 1. 先说清用户要完成什么

- 从现有材料确定谁使用、在什么情况下使用、要完成什么、怎样知道完成。缺少会改变业务行为的规则时，按全局规范第 8 节处理；不要把技术选项或整套设计问卷交给用户。
- 新功能先用简短说明或小表写清“用户任务、入口、主要动作、结果与后续”。涉及多页时再画必要的页面关系图；小修改不用另写设计文档。
- 每个字段、按钮、统计数和页面区块，都应帮助用户判断、操作或理解结果。说不出具体用途的先不展示；接口、数据库表和后台模块的数量，不决定菜单和按钮数量。例如工作人员只需处理待办，缓存刷新和任务重试通常属于维护人员的工具。
- 先露出当前任务需要的内容，低频设置和补充信息放到明确可找到的位置。精简时保留必要条件、费用、错误和重要后果；不要把常用操作都藏进“更多”。
- 一个操作区有明确的主要动作，其他动作区分轻重。按钮用具体动作和对象命名，例如“保存草稿”“提交申请”；同一个按钮不要暗中完成用途不同的操作。多个后台步骤可以支持同一个用户任务，前提是按钮名称和结果符合用户预期。

## 2. 页面层级和打开方式

导航按用户任务和业务对象组织。顶部适合跨业务区域或全局操作，侧边适合当前系统的主要业务入口；小系统可以只选一种，不重复摆两套菜单。标签页切换同一对象的相关内容，面包屑说明真实的上下级关系，当前所在位置有明确标记。不要为了少点一次，把全部层级铺在一页。

按任务持续时间、信息量和是否需要保留当前位置选择打开方式，沿用项目中同类操作的安排：

| 用户在做什么 | 优先考虑 | 需要注意 |
| --- | --- | --- |
| 改一个简单字段、展开补充内容 | 页面内编辑或展开 | 保存、取消和修改范围清楚，不让原内容突然移位 |
| 选择一个局部操作或短选项 | 菜单、小浮层 | 不塞长表单；点击范围和键盘操作明确 |
| 在列表旁快速看详情、处理短任务，完成后接着看原列表 | 抽屉或侧面板 | 保留列表位置；内容需要长期阅读、分享或复杂编辑时转独立页面 |
| 短而集中的决定，需要暂停当前操作 | 弹窗 | 说明对象与后果，有清楚的退出办法；不要用来承载完整业务页面 |
| 独立任务、长表单、多步骤编辑，或需要直接链接访问 | 独立页面；确有先后依赖时分步 | 能返回，能识别当前步骤，必要时保留草稿 |

抽屉描述打开位置，是否阻止操作背景页面要另外决定。需要一边看列表一边编辑时，采用可同时操作的布局；阻止背景操作的弹窗或抽屉，要处理键盘进入、退出和关闭后的返回位置。

不连续叠加抽屉和弹窗来代替页面层级。短确认可以中断当前编辑，但复杂后续任务应有自己的页面。关闭面板、返回上一页、取消编辑的含义不同，不能都跳回首页；返回列表时保留有关的筛选、排序、分页和位置。需要直接访问的详情页，也要检查刷新、复制链接和浏览器返回。

## 3. 把操作前后设计完整

关键操作先明确：什么状态能做、处理时怎样显示、成功后去哪里、失败后怎样继续、能否更正或撤回。状态来自业务规则和实际结果，界面不能替后台编造成功。

| 情况 | 界面应怎样处理 |
| --- | --- |
| 正在读取 | 显示正在加载，保持主要布局稳定；不要先闪出“暂无数据” |
| 没有记录或筛选无结果 | 分清首次无数据与条件无结果，提供当前用户能用的下一步，例如创建或清除筛选 |
| 正在提交 | 显示处理中并避免重复操作；防止重复写入还需要服务端保障 |
| 已完成 | 更新真实状态，指出结果和有用的下一步；重要业务结果有可再次找到的记录，不能只靠一闪而过的提示 |
| 确认失败 | 在相关位置说明哪里失败、怎样处理，保留能保留的输入，提供适用的重试或修改入口 |
| 超时且结果未知 | 先查询是否已完成，避免直接重提造成重复记录；不把连接中断写成业务必然失败 |
| 无权限或当前状态不能操作 | 根据业务需要隐藏入口，或说明原因及能做的事；界面隐藏不能代替后台权限检查 |

能否撤回由业务状态决定。提交前可以取消编辑；提交后可能允许撤回、更正、申请取消，也可能已经无法撤销。说清条件、后果和后续办法，不为了按钮成对而编造能力。涉及审批、状态变化或用户需要凭据的任务，在现有详情或记录入口显示谁在何时做了什么、结果是什么；简单偏好开关不用另建记录中心。

表单在输入处写清名称、必要格式和出错原因，占位文字不能代替字段名称。离开未保存内容时，按实际保存方式提供继续编辑、保存或放弃；只有确有重要后果才增加确认，不让每个普通操作都弹窗。

## 4. 统一视觉与中文表达

先确定页面用途和一个一致的视觉方向。操作密集的页面重视扫描、比较和处理速度；展示页面可以更有表现力。用真实长度的中文、数字和多种状态检查排版，不只拿几条整齐的短文字判断效果。

### 4.1 公共样式

颜色、字体、字号与行高、间距、圆角、阴影和动效在公共样式中统一定义，页面引用有含义的变量。同一用途保持同一种样式，错误、警告和成功颜色不要随着主题随意互换。

- 使用组件库时，先用它支持的主题与组件配置。确需补充 CSS 时，集中放在受控的覆盖位置并限制影响范围，不修改依赖源码，不到处叠加深层选择器和 `!important`。
- 自写组件时，共用按钮、输入框等确实重复的部分，业务页面保留自己的布局。按现有结构组织，不为一页创建完整组件平台；同一组件的正常、悬停、键盘选中、处理中、禁用和错误显示保持一致。

### 4.2 背景和排版

背景可以用与主题色有关的淡色、细纹理或条纹增加细节，适合时使用；文字、表格和表单区域保持易读，不能为了纹理牺牲对比度。通过间距、分组、字体和必要的分隔线表达层次，不把每段内容都套进卡片。

默认不用左侧高亮竖条的大卡片，不给每个标题固定配一行重复意思的小字说明，不堆装饰性大标题、无用统计卡和占满首屏的横幅。这是本套规范的视觉选择；已有项目的明确品牌要求优先。必要帮助放在真正需要解释的字段或操作旁。卡片只在一组内容确实需要独立浏览、比较或操作时使用。

### 4.3 字体与文案

按标题、正文、字段名称、辅助说明和数字等用途确定字体样式，同类内容统一。屏幕界面优先保证中文阅读、字形和备用字体可用；表格数字便于纵向比较，金额、单位和关键状态不因省略或换行造成误解。

公文、报告的预览或导出，按已确认的文种、客户模板和适用规范另设排版；操作按钮和列表仍使用界面字体。文档规范不明时先查模板，不凭“正式”二字给整个后台套印刷字体。

界面文字遵循全局规范第 9 节，具体改写参考同级 pre-delivery-check 的 `references/wording.md`，不复制词表。直接写业务名称、动作、条件和结果；避免开发术语、空泛口号和重复解释，正常业务术语按项目约定保留。界面不用日常聊天的表情。

## 5. 动效与不同使用方式

动效说明展开、收起、状态变化和操作反馈，方向与元素位置相符，时间简短一致。不要每个区块都做入场动画，不为了等待动画结束而延迟操作；尊重系统减少动态效果的设置。

页面能用键盘操作，选中位置可见，控件有可理解的名称；颜色之外还有文字或形状说明状态。弹窗使用成熟组件或正确的网页语义，打开后能进入、关闭后回到合理位置，键盘不会困在无出口的区域。

按目标设备检查小屏、文字放大和触屏操作，保留主要任务，点击范围不拥挤。窄屏不要把桌面抽屉压成一条细缝；需要时改为整页。宽表格可局部横向滚动，普通正文和表单不应被整页横向滚动挤出屏幕。具体对比度和操作要求参考 [场景与资料](references/patterns.md)。

## 6. 怎样完成设计与检查

新建或大改页面时，先做能操作的主要任务，再扩展相关页面。保留重要取舍的简短说明，让用户能检查入口、打开方式和结果；不为已有清楚约定的细节增加批准步骤。

交付时沿用 pre-delivery-check：亲自从任务入口操作到结果，再查看返回、取消或失败后的恢复；检查本次涉及的键盘操作、窄屏和公共样式。选择有不同用法的代表页面，不反复检查无关页面。原型只有模拟数据或尚未连接服务时如实说明，按钮出现不等于功能已经可用。

发现问题按影响处理：用户无法完成、容易误操作或误解结果的先改；再处理影响阅读的排版和不一致。操作已顺畅、相关检查完成后结束，不为不断变换风格继续打磨。业务正确性、实际可用、视觉偏好分别说明，截图好看不能证明前两项。

遇到页面安排、操作恢复、字体用途的争议时，读 [场景与资料](references/patterns.md) 中对应部分；资料供判断，不要求每次把全部设计系统读一遍。
