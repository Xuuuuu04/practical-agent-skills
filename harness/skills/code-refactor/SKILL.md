# 代码重构与整理

让指定包更好理解、更容易改动，保留已确认的对外行为。整理的价值在于减少重复和牵扯，文件整齐只是其中一部分。

## 1. 看清范围和原状

用户已指定包与顺序时逐个完成；只说整理整个项目时，先给包的大小、实际问题和推荐顺序，请用户确定。由当前 Agent 处理，其他安排沿用用户与项目规定。

读清调用入口、接口、表、配置和定时任务，确认哪些对外行为要保持。改动集中在指定包，移动改名所需的包外引用和项目说明一并更新；其他问题提出建议。

记下提交编号，保护将改动的未提交和未跟踪文件；Git 提交不能代替这些内容的备份。运行已有测试，补充未覆盖入口的输入与旧输出。时间、随机编号等先明确比较方法，已知旧错误与行为比较分开处理。

运行 `python <本 Skill 所在目录>/../pre-delivery-check/scripts/change_health.py --repo <项目根目录> --package <包目录>`，把提示与实际用途一起看。

## 2. 让结构表达业务

同一规则集中维护，不同用途保持清楚；模块间的依赖方向可见。重叠文件讲不清拆分理由时合并，正常的独立业务不为减少文件数硬合。后端结构参考 backend-architecture-design。

清理无用内容前，检查调用、配置、动态加载、脚本、命令入口与文档链接，并找替代实现、废弃说明或执行结果。搜索不到引用只是一条线索。用途不明的资料先保留，客户交付文档、真实数据的删除沿用全局第 8 节。

现有包 README 随结构更新，项目入口变化用 project-agents-md。注释、命名、中文和本机资料分别沿用全局第 6、9、5 节。

## 3. 用长度提示检查结构

项目已确认限制优先，默认值与 pre-delivery-check 脚本一致：

| 对象 | 默认上限 |
| --- | --- |
| 代码文件 | 400 行 |
| 函数 | 60 行，脚本只检查 Python，其他语言人工看 |
| 文档 | 300 行 |
| Shell 脚本 | 200 行 |
| SQL | 单条语句 80 行 |
| 日志 | 每条一行，记录能定位问题的关键字段 |

超限先找重复与独立业务步骤。连续计算不适合硬拆时，说明原因、影响和检查办法，按全局第 8 节处理必要取舍；避免压成一行或拆出无用途的碎文件。

## 4. 用前后结果判断完成

每组完整改动比较实际受影响的入口，最后完成包的整体比较。相同输入与初始数据应符合已确认的兼容规则；发现差异时用 debug 查明原因，整理引入的错误修正，旧错误说明后按授权处理。

再查接口、表、配置和定时任务，运行开始时的结构检查。预期之外的行为变化、规则冲突和未授权的对外变化，沿用全局第 8 节；独立部分继续。

按 pre-delivery-check 交付，说明现在好找、好改在哪里，行为比较和必要检查的结果。移动、合并、删除的原因可从实际差异查看，未验证部分直接说明。
