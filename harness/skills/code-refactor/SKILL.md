# 代码重构与整理

## 1. 目的

把指定包整理得更容易理解和修改，保持已确认的对外行为。开始前给出自己的建议：哪些实际问题值得处理，哪些做法会增加文件和理解成本。结构已经清楚时，不为了形式统一继续拆分；完成约定范围、前后比较通过就结束，不追求消除所有可改进之处。

## 2. 使用范围

1. 只在用户点名要整理的包时使用。用户说"整个项目都整理一下"时不要直接开始：列出各个包的大小和主要问题，请用户挑第一个，或者给出顺序。
2. 一次只处理一个包，默认由当前 Agent 自己做。用户已经指定多个包和顺序时，完成一个再继续下一个，不重复确认；只有用户要求逐包验收，或出现全局规范第 8 节规定的新问题时才等待。是否使用子代理按用户要求和项目规定处理。
3. 不改指定包之外的文件。例外是文件移动或改名后更新包外引用，以及同步受影响的项目 AGENTS.md；包外发现的问题只报告，不动。

## 3. 开始前

1. 弄清对外的影响面：这个包被哪些别的包调用，对外提供哪些接口、数据库表、配置项和定时任务。这些是不能悄悄改变的部分。
2. 保证有回退点：记下当前提交编号，并保存将要改动的未提交文件副本。无关改动不触碰；只有无法安全分开时才请用户处理，不强迫先提交。git 不能找回未跟踪文件或未保存的修改，不把提交编号当成它们的备份。
3. 记录整理前的行为：先运行这个包已有的测试并记下结果；测试没有覆盖到的入口，准备样例输入，记下整理前的输出。整理后用相同输入和初始数据再比较。按全局规范第 6 节区分行为不变与业务正确；时间、随机编号等先确定比较办法，已知旧错误单独报告，不悄悄保留或修正。
4. 看一遍现状：运行 `python <本 Skill 所在目录>/../pre-delivery-check/scripts/change_health.py --repo <项目根目录> --package <包目录>`，列出这个包里超长、缺注释、用词晦涩的地方。

## 4. 整理规则

### 4.1 清理无用内容

要删除的：无效代码、无效文件、历史版本文件（比如旧版没人用的 `xxx_old`、`xxx_backup`）、记录改动的注释、被注释掉的代码、历史修改记录、交付文档。先证明它已无用途，再删除；暂时说不清用途只表示尚未查明，不等于无用。

删除之前逐个确认：

- 检查调用、配置、脚本、自动化流程、动态加载、命令入口和文档链接。搜索不到引用不足以证明无用，还要有替代实现、废弃说明或执行结果等依据；用途不明的保留并报告。
- 交付文档可能是要交给客户的，单独列成清单给用户确认，不要和无用文件一起删。
- `.agent/`、`AGENTS.md`、`.gitignore` 不删。

### 4.2 结构：高内聚低耦合

- 同一业务规则只保留一份实现；不同入口可以共用它。文件和脚本按实际用途组织，不为追求数量少而合并不同用途。
- 两个文件做的事有重叠，又讲不清楚为什么要分开，就合并，或者删掉一个。
- 必须保留的文件、散落各处的同类内容，归到同一个目录，名字体现它们之间的关系。
- 包内部的依赖方向要清楚，不能出现两个模块互相引用。

后端项目同时参考 backend-architecture-design Skill 的检查项。

### 4.3 同步说明文档

包里有 README 时，对照整理后的实际情况更新：目录结构、怎么运行、对外接口、注意事项。没有 README 的包，不为这一步新建。项目根目录的 AGENTS.md 因此需要变化时，按 project-agents-md Skill 更新。

### 4.4 长度限制

下面是默认长度限制，项目已确认的限制优先。超限时先删重复内容、按实际业务步骤拆分，不能把多行挤成一行，也不为过检查增加只负责两三行代码的文件。真实的连续计算不适合硬拆时，说明具体原因、影响和检查办法；是否需要决定按全局第 8 节处理，不私自放宽整个包的规则。

| 对象 | 默认上限 | 脚本能否检查 |
| --- | --- | --- |
| 代码文件 | 400 行 | 能 |
| 函数 | 60 行 | 只检查 Python，其他语言人工看 |
| 文档（.md） | 300 行 | 能 |
| 脚本文件（.sh） | 200 行 | 能 |
| SQL | 单条语句 80 行 | 能 |
| 日志 | 每条一行，不打印整张表或整个响应，只打印能定位问题的关键字段 | 不能，人工看 |

### 4.5 注释和命名

按全局规范第 6 节的注释和命名标准，说明类、业务入口和关键规则，避免逐个翻译名字清楚的简单变量。脚本的缺注释提示只是待检查项；说明是否有用、关键业务量的单位和边界要人工看。

### 4.6 用词

包内注释、文档、界面文字和日志文案按全局规范第 9 节处理，保留正常技术含义和已确认业务用语。词表和写法见 pre-delivery-check Skill 的 `references/wording.md`，脚本会按它扫描。注释要从应用层讲这段代码在系统里的作用和位置，让人一眼看懂，少讲实现细节。

### 4.7 精简和优化

可以合并重复的逻辑、去掉多余的判断、提高性能。有两条限制：

- 会改变行为的优化（比如改变结果的顺序、去掉某个看似多余的检查），先向用户说明，同意后再做。
- 一组有关的修改完成后，对比受影响的入口和样例；不为每次移动或改名重复跑完整检查。最终仍完成包的整体比较。

## 5. 做完之后

1. 用整理前记录的测试和样例再跑一遍，结果一致才算完成。有差异时，先查清是整理引入的还是原本就有的问题：整理引入的改回去，原本就有的记下来交给用户，不顺手改。
2. 重新运行开始前的脚本，确定问题已处理，待人工检查的提示已判断；误报和不改的项写明理由。
3. 检查对外的影响面：接口、数据库表、配置项、定时任务有没有变化。没有变化才算安全。
4. 按 pre-delivery-check 交付。交付说明里写清：删除了哪些文件、每个文件为什么删；移动或合并了哪些文件；整理前后对比了哪些样例；哪些地方没有验证。

## 6. 需要决定的情况

- 要改变尚未授权的对外接口、数据库表结构、配置项名称或业务结果。
- 要删除仍有用途的文件或交付文档。已授权的文件移动、改名和对应引用更新，按使用范围处理，不因存在引用而重复确认。
- 整理前后的行为对比有差异，又说不清是不是原本就有的问题。
- 包内有两套互相冲突的做法，不知道保留哪一套。

这些情况统一按全局规范第 8 节判断是否等待；不依赖这个决定的部分继续做。
