# 会话交接

让未参与本次讨论的 Agent 能接着做事，知道目标、实际状态、已经确定的要求，以及哪些地方不能凭猜测继续。直接输出可复制的中文 Markdown，内容独立可读，不依赖“上面说过”的信息，不生成总结文件。

## 1. 先确定交接时的实际状态

用户要求停下并换会话时，停止扩展原任务，完成必要的只读检查后输出交接。不要为交接继续实现、提交、发布、重跑完整测试或新建任务文件，也不把未完成的原任务标为完成。生成交接内容不包含创建新会话、发送给其他会话或保存长期记忆；这些操作按用户另行明确的要求处理。

先整理当前可见的对话、用户最新要求和已有结果，再按缺口读取本项目有关的说明、任务、决定与文件。只查会影响接手的内容，不遍历无关项目或全部历史会话。旧总结与当前文件或新决定冲突时，说明差别并采用能确认的最新事实。

涉及正在开发的项目时，查看当前工作目录、分支、提交与未提交改动；区分自己的修改和其他人的修改。读取实际检查结果，记录检查针对哪个版本；之后又改过的部分不能沿用旧结果声称通过。只记录确实查到的路径、命令和编号。

后台任务、其他 Agent、部署或外部请求仍在运行时，说明对象、所在目录、可用编号、最后已知状态和查询方法。停止回复不代表这些工作已停止；结果未知的写明未知，不建议新会话直接重发可能重复执行的操作。

## 2. 按接手顺序组织内容

开头先写项目理解与当前目标，指出最重要的未完事项；中间放理解和执行所需的材料；结尾给出接手后的第一步。使用下面八部分作为默认骨架，可合并无关小节，不为凑结构填空话。用户要求简短时压缩背景，保留决定、未完事项、重要缺口与下一步。

### 2.1 项目理解与当前目标

说明项目服务谁、最初解决什么问题、希望得到什么结果，以及本轮工作处于整体计划的哪一步。给出你对当前方案的判断、简短依据和仍有的分歧；把事实与建议分开，不虚构规划，也不写人物评价。

紧接着用几句话写清当前停在哪里、接手最先需要注意什么。只在取得系统时间后写状态时间；没有新检查时明确哪些状态来自先前记录。

### 2.2 核心内容、文件组织与设计

按业务用途介绍关键目录、入口文件、主要模块和它们的关系，说明数据怎样经过这些部分、为什么这样安排。列出会影响继续工作的文件路径与用途，不抄完整目录树，不逐个介绍无关文件。非代码项目改写为材料、文档或成果的组织方式。

区分当前已经存在的设计与尚未实施的建议。若有独立工作目录、公开副本、生成文件或安装副本，指出应该改哪份内容、其他副本怎样更新，避免新会话改错位置。

### 2.3 可用资源与运行方法

列出后续会用到的资料、样例数据、脚本、工具、服务和成果位置，写明用途。对关键命令说明在哪个目录执行、需要什么前提、会读取或修改什么，以及是否实际运行过。

保留重要版本、配置项名称和有效的查看入口；不复制密钥、访问令牌、会话凭据或与任务无关的客户资料。只能在原机器访问的路径或工具要说明，新会话无法访问时给出已有的替代入口，不编造替代资源。

### 2.4 已验证的工作流程

说明本次实际摸索出的有效顺序，例如先看哪份业务说明、用哪个小样例复现、修改哪个模块、运行哪些必要检查、怎样判断结果。区分已运行的做法与建议步骤，不把一次偶然成功写成普遍规则。

列出继续工作容易重复踩到的问题、已排除的办法和排除依据；保留最近一次失败的具体条件，以及什么新事实出现后才值得重试。不复述每轮试错，也不加入与接手无关的过程记录。

### 2.5 用户要求与已确定的选择

整理会改变后续做法的业务要求、设计与审美偏好、中文表达、工程投入、验证办法和交付方式。优先写本项目与当前任务的具体要求；公共规范保留入口，不整份复制。

明确区分用户已确认的要求、Agent 的建议和从交流中推测的偏好。推测写出依据及不确定处，只用于理解，不变成新功能、业务规则或授权。用户没有回答不能写成同意；要求前后变化时保留最新决定与受影响范围。

已有授权写清对象、环境、范围和条件，避免接手后反复询问，也避免扩大到其他对象。等待条件仍按适用的全局规范判断，不在交接中另设规则。

### 2.6 已完成与未完成的工作

按工作项汇总当前任务及仍会影响后续的前序工作。每项说明目标、实际结果、相关文件或提交、检查依据和剩余部分。已完成、实现但未检查、正在进行、等待决定、尚未开始分别说明；合并、发布和真实业务验证不能混为一个“完成”。

未完成项写清最后推进到哪一步、正在排查什么、已有证据与具体困难。不要漏掉未提交文件、临时成果或仍在运行的任务；成果在临时目录时注明可能失效。旧任务文件只作线索，未确认还有效的事项单独说明，不自动恢复已取消的工作。

### 2.7 信息缺口与记忆不确定处

主动指出已意识到的缺口：哪段对话当前不可见、哪个决定只剩模糊印象、哪次检查缺少原结果、哪些资料互相矛盾。每项说明可能影响什么，以及能去哪里查或需要用户回答哪个具体问题。

当前看不到的细节不要靠顺畅叙述补齐。无法知道丢失了哪些内容时，说明可见范围，不能声称已经找回全部历史；没有发现具体缺口时也不为了这一节编造遗忘事项。缺少信息不能写成“没有要求”或“没有做过”。

### 2.8 接手后的行动与后续考虑

按先后写出少量能执行的下一步：先查看什么或做哪个小检查、希望得到什么结果，再根据结果推进哪一项。必须等待的部分写清所缺答案；不依赖它的工作继续安排。接手时先检查目录、版本和运行状态是否变化，不假定交接时的状态一直有效。

较远的改进想法单独标为建议，说明价值和考虑它的条件；没有依据就不写，不把愿景混进已授权任务。最后用一句具体行动结束，让新会话知道先从哪里开始，不再重复整份总结。

## 3. 输出前检查

- 新会话能否仅凭这份内容找到项目、理解目标、分清已做与未做，并执行第一步？关键判断是否有依据或明确标出不确定？
- 是否遗漏会影响业务结果的条件、用户反对过的做法、尚未兑现的已确认要求、未提交改动或运行中的工作？
- 是否误把旧结果当作当前状态、建议当成决定、未运行当成通过？是否包含不应复制的敏感值？
- 中文是否连贯、对象是否清楚？删除重复背景和流水账，保留关键事实；不强行规定总字数，也不把交接压成只有路径的清单。

完成交接后结束本轮回复，等待用户在当前或新会话给出后续要求；不要在交接末尾又开始执行原任务。
