# 交付前检查

交付意味着有人接下来要使用和维护这份结果。检查它是否解决了原问题，修法是否放在合适的位置，实际结果是否支持完成的说法。

## 1. 先看目标与证据

从用户要求、项目规则、确认样例和实际差异确定检查范围。预期从业务规则来，当前实现和旧系统输出用于比较实际行为。规则不明用 business-rules，错误原因未明用 debug。

检查与改动的实际影响相称：简单文字看文字，共用计算看有关入口，金额、权限、删除、迁移、并发和定时任务查看相关保存与失败处理。项目必需检查继续执行，已有证据可用时直接使用。

## 2. 文件与代码检查

代码或结构变化运行 `python <本 Skill 所在目录>/scripts/change_health.py --repo <项目根目录>`。默认比较最近一次提交及工作区；已提交改动用 `--base main` 或 `--base HEAD~1` 指定起点。

脚本检查长度、注释、用词、遗留内容和错误处理，只能判断相应文件规则。确定问题处理，提示结合实际用途判断；正常记录并抛出的异常、准确技术用语等保留原因，避免为了消除提示破坏设计。

查看真实差异与相关调用，尤其检查：

- 业务规则是否放在合适的模块，同一原因造成的错误是否覆盖实际受影响的入口。
- 是否为通过一个样例加入重复补丁、绕过模块接口、吞掉失败或改松测试。
- 搜索、分页、导出、保存和外部动作是否遗漏相应变化。
- 新增文件、依赖与抽象能否说清用途，原补救是否已失去作用。

发现问题给出输入、操作或代码与规则依据。已证实且影响本次交付的错误处理后，再检查修复及影响；一般建议按价值报告，必要取舍沿用全局第 8 节。

## 3. 业务与页面验证

运行本次适用的测试，用独立样例比较应得与实际结果。真实 bug 留下能重现原条件的测试；重复操作、空值、退款和失败等在与原因或规则相关时覆盖。迁移或前后比较区分行为一致与业务正确。

界面变化时，按 interface-design 操作实际受影响的页面。使用 ego 浏览器及其 Skill，没有时采用可用的浏览器办法；无法操作就列出未验证的页面。

从入口走到结果，检查字段、合法空值、金额、单位和状态，再试有关的返回、取消、失败与恢复。选代表记录，把业务预期、接口数据和显示逐层比较；页面与接口相同只能证明显示一致。共用组件覆盖有不同用法的代表页面。

## 4. 检查提示词与文字

维护协作规范或 Skill 时，读 [行为检查](references/behavior-checks.md)，看工具实际读到什么、遇到场景怎样选择。被测工具只读任务需要的规范，不读含判断答案的题库。情境回答与真实长任务效果分别记录。

文字遵循全局第 9 节与 [写法说明](references/wording.md)。脚本提示用词，人检查整句话：对象、动作、条件、数字和完成程度是否清楚，有无重复、空话或无依据的赞同。规则示例只跳过词语匹配，其他检查照常。

## 5. 收拾好再交付

按全局第 5 节清理本次用完的脚本和输出，保留仍需复现、恢复或查看的最少证据，并说明用途与可删除条件。检查引用，避免删除唯一证据后仍给出失效入口。

提交按全局第 6.1 节查看实际内容，保留他人的工作和敏感资料；并行工作合并后检查共同影响。相关检查完成、已发现的交付问题处理完，就给用户结果。

回复先说现在能做什么、还差什么、去哪里看。金额、状态和权限先讲一条具体业务结果。实现完成、检查完成、已提交、已合并、已部署和生产实际使用分别报告，缺哪项就说哪项；有重要缺口时交付进度与证据。

检查过程可以细，反馈用大白话。正式报告按要求展开，日常几句话说明实际结果，文件和检查记录放在有关句子旁。
