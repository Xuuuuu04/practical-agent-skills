# 交付前检查

## 1. 目的

检查功能是否可用、业务数据是否正确，以及当前改动是否让代码更难理解。用具体页面、样例和运行记录说明结果，让不读代码的人也能判断完成程度。

开始时先问：本次结果能不能达到用户目标，选定的检查能证明什么。发现方案或验收办法有重要问题，先提出依据和替代建议，不能只检查实现是否照着要求写了。

检查的多少由实际风险决定，既不省掉必要检查，也不为追求更保险反复加检查。相关检查通过、已发现的影响交付的问题处理完，就交付；只有新的失败、改动或具体风险才扩大或重复检查。已证实的严重错误仍要处理。

## 2. 机械检查

负责检查其他工具的协作规范或 Skill 时，读取 `references/behavior-checks.md`；作为被测工具回答情境时不读取题库。区分读取情况和操作选择，不把情境回答当成长任务效果的证明。

项目有自己的检查命令时（写在项目 AGENTS.md 的"怎么运行"里，例如测试、lint、质量检查），运行适用于本次改动的命令；项目明确要求的完整检查也要完成。纯文字评价只用相关原则，不运行无关功能检查。

代码或结构改动运行本 Skill 的脚本；只改文字时，按第 9 节和 `references/wording.md` 检查用词与句子，不运行无关代码检查：

`python <本 Skill 所在目录>/scripts/change_health.py --repo <项目根目录>`

脚本只读文件，默认比较最近一次提交，包括未提交改动和新文件；已提交的改动用 `--base main` 或 `--base HEAD~1` 指定起点。它检查长度、注释、用词、遗留内容和错误处理，区分确定问题与待人工检查的提示；不替代语法、类型、业务和实际页面检查。

本次新增或加重的确定问题改掉，原有问题不扩大处理；结合开始时的文件判断归属，不把全部未提交改动算成自己的。提示逐条判断，误报说明理由；按全局第 6、9 节保留准确的技术、业务含义和合理的错误处理，不为了消除提示机械修改。缺少检查时如实说明。

中文表达按全局规范第 9 节。脚本只提示用词，整句话和段落仍需人工读：对象和动作是否清楚，条件、数字和完成程度是否准确，是否有空话或重复结尾。明确标注的规则示例与测试文本只跳过用词匹配，其他检查仍执行。

## 3. 功能验证

- 运行和这次改动相关的测试。
- 先使用已有检查；补测试要能发现一个具体错误，例如同一订单被重复处理。已有结果足以证明的简单改动，不另造一套测试。排查脚本和提示词试验放临时目录；会长期重复使用的功能测试，按项目约定保存。
- 业务规则或预期结果不明时，用 business-rules 查已有依据并整理样例；不从当前实现反推应得结果，等待条件沿用全局规范第 8 节。
- 后端改动：用真实或样例数据调用受影响的接口，把返回结果和业务文档里的规则或样例对照。
- 涉及计算、数据转换、业务规则时，准备三到五条对照样例：输入、按业务规则应得的结果、实际结果。样例要包括容易出错的情况，比如退款、空值、重复记录。
- 修复真实 bug，以及新增金额、权限、数据转换等重要规则时，留下对应功能的测试；低风险简单改动不堆一次性测试。样例数量由规则和风险决定，三到五条是展示用的代表样例，不能据此认定复杂功能已全部覆盖。

## 4. 界面验收

改动会影响界面显示时做这一步。涉及导航、操作方式或视觉方案时，结合 interface-design Skill 判断是否便于使用；不因此扩大检查范围。用 ego 浏览器，具体操作按 ego 自带的 ego-browser Skill 进行。没有 ego 时，用当前工具能用的浏览器自动化方式；都没有，就在交付说明里写明"界面未验收"，并列出用户需要自己点的页面。

1. 列出实际受影响的页面和操作，包括有关的子页面、标签页、弹窗和详情页；共用组件影响多个页面时，检查有不同用法的代表页面。只改一个页面，不重查无关页面。
2. 找到标准：需求、业务文档和已确认样例中的字段及计算规则。清单缺失时，结合这些材料起草，标明待确认；当前页面只说明现状，不能证明没有遗漏。无法确定的字段含义暂停相关改动，其他检查继续。
3. 逐页对照：
   - 应显示的字段都显示了，合法空值按约定展示，没有意外空白或 undefined、null、NaN；
   - 挑两三条记录，先用业务规则和独立样例确认接口结果，再把页面显示与接口或数据库逐字段比较；页面与接口一致只能证明显示一致，不能单独证明计算正确；
   - 至少看一种特殊情况，比如空列表、字段为空、金额为零或者有退款。
4. 在交付说明里写清：看了哪些页面、对比了哪些记录、发现了什么。

## 5. 代码审查

每次代码改动都检查实际修改的内容，确认它符合需求、没有漏掉调用处和容易出错的情况；例如搜索条件、分页和导出要看是否漏数据。已有检查能证明的结果不重复测试。

金额和计价计算、数据删除或迁移、权限和认证、并发和定时任务等高风险改动，再深入检查实际受影响的调用、数据保存和失败处理。不要因此全面检查无关代码；纯文字修改跳过代码审查。

- 范围以这次修改及其实际影响为限。
- 需要修正的只有四类：功能会出错、数据或金额会算错、安全问题、违反适用的全局或项目规则。每条附具体输入、操作步骤或足以证明错误的代码与规则依据；只有猜测的列进建议，不改。不要求为危险操作在真实环境重现错误。
- 修的时候改掉出错的原因，不要靠宽泛的异常捕获或层层判空来掩盖。
- 第二轮只检查修复及其影响。无关的一般建议报告后停止；新发现的已证实严重错误仍要修复并检查，超出授权或缺少规则时暂停交付受影响部分，不重新启动全面找问题。
- 默认由当前 Agent 检查。只有用户要求或项目明确允许时，才使用一次范围明确的只读子代理；给它相关业务规则和限制，不让它反复扩大问题清单。

## 6. 什么时候算检查完

完成程度分开说明：

- 实现完成，可供检查：改动已写好，能运行的检查已做；列出尚未完成的检查和原因，不称为验收通过。
- 检查完成：适用的机械、功能、界面检查和代码审查已做，提示已判断，已证实会影响本次交付的错误已处理。缺少测试或工具时说明采用了什么替代检查及其局限。
- 已部署：只在明确授权的部署实际成功后这样写；实现或检查完成不等于上线。

没有重要缺口时结束检查，不为了更保险扩大范围。还有严重错误、业务标准未定或必要检查缺失时，可以交付进度与可检查的文件，但不声称相关功能已完成验收。

## 7. 交付说明

涉及 Git 交付时，按全局规范第 6.1 节检查将提交的文件、改动内容和中文提交信息，确认没有带入别人的修改、密钥及临时文件。并行改动合并后，检查共同影响的功能；已有项目要求的检查照常完成，不另设一套流水线。

写明实际提交号或 PR 地址，分别说明本地检查、提交、合并、发布与生产检查做到哪一步。未执行的步骤不写成完成；本地通过不能代替生产环境结果。

按全局 AGENTS.md 里的交付说明格式写，其中"怎么验证的"要写具体：运行了哪些检查及结果，看了哪些页面、对比了哪些记录，运行编号或 trace_id。脚本报出的"原有"问题和明显的异常（比如某个文件超过 400 行、这次新增了很多文件）写进"质量提醒"，没有就不写。
