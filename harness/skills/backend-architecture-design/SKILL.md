# 后端架构设计

## 1. 确定设计范围

读项目设计、业务和代码，沿用已有技术与接口。用一笔业务说明入口、计算、保存和外部动作，再安排模块；新机制说明实际用途、影响与维护成本。

以下执行顺序图、模块清单和组件规则用于本套框架，不要求其他已有后端照搬。

## 2. 模块与依赖

模块按独立业务划分，维护规则与处理步骤。公共框架提供连接、事务、分页、计时和错误转换，不能依赖业务模块。

本框架用静态执行顺序图定义组件、顺序和条件；简单业务可只有一个节点。组件各做一件事，执行器记录实际步骤、耗时和失败。

模块清单声明接口、依赖和原因。跨模块只调用已声明的公开接口，内部代码与存储实现留在本模块；启动检查注册、引用和依赖完整。

结构视图从代码生成，业务文档解释含义，运行轨迹记录实际过程，三者不重复手工维护。

## 3. 数据与保存

Pydantic 表达数据格式，字段说明含义，必要时补来源、单位和计算方法。存储模型由数据访问层管理，业务经仓储接口读写；外部平台数据由适配器转换。

业务确定哪些修改一起成功或撤回、哪些可分批，以及权限和数据隔离规则；框架执行这些要求。未定规则用 business-rules。

节点默认记录输入输出摘要，敏感字段脱敏；额外字段、采样和保留期按定位需要与存储成本确定。

## 4. 入口与运行

成功响应沿用项目约定。错误区分参数、资源、业务与系统问题，包含错误码、说明和请求编号；详细错误留在运行记录中。

请求、后台任务与外部调用保持关联，提供按 `trace_id` 或业务编号查询、导出的入口。现有日志足够时直接使用，完整追踪平台按实际需要采用。

字段或格式的版本差异在入口转换；计费、退款或权限差异先确定兼容规则。确认旧版本无人依赖后再移除。

耗时、重试或高峰削减确有需要时用队列，并说明运维代价。部署、健康检查和性能检查按目标环境安排；状态放数据库或缓存。

共用入口处理输入校验、参数化查询、认证、权限、CORS、适用的限流与日志脱敏。配置集中读取并在启动时校验，缺必需项明确失败，`.env.example` 说明配置。

## 5. 文档与迁移

模块 README 给业务用途、接口、依赖、流程和设计原因；可生成信息来自清单。业务文档维护计算、字段、权限与保存规则，项目入口用 project-agents-md。

迁移一次一个业务单元，先选能经过主要读取、计算、保存和接口的模块：

1. 固定旧版本，协调迁移期间必要修改。
2. 准备请求和结果样例，确定动态字段比较与已知旧错误的处理规则。
3. 默认保留表、前端、接口和格式；必要差异明确转换、迁移与恢复办法。
4. 新旧写入从相同隔离初始数据运行，付款与通知用替代服务。
5. 比较全部差异，完成部署、性能与兼容检查后按授权切换；同一请求只由一套后端处理。

[模板](references/templates.md) 按需查用；[质量检查](references/quality-checks.md) 只选适用项。公共层变化覆盖受影响模块，交付用 pre-delivery-check。
