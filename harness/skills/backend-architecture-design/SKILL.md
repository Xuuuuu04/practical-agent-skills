# 后端架构设计

好的结构让业务容易表达、变化容易安放、错误容易找到。按稳定可用、容易理解、容易修改、性能的顺序取舍，同时满足项目的权限与数据保护要求。

先读项目 AGENTS.md、相关模块和业务说明，沿用已确定的结构与技术。下面提供本套 FastAPI 单体框架的设计方法；已有系统的成功响应、ORM 和模块方式以实际约定为准。框架能力随真实业务需要增加，每项说明用途与维护代价。

## 1. 先看业务怎样经过系统

用一笔具体业务说明入口、计算、保存和外部动作，再安排模块。遇到重复错误时用 debug 找实际原因，确定是实现问题还是结构使同类错误不断出现；结构调整照顾所有实际受影响的入口。

把几个对象分清：

| 对象 | 表示什么 |
| --- | --- |
| 执行顺序图 | 代码中的静态定义：组件、顺序和条件，是模块处理结构的来源 |
| 运行轨迹 | 一次操作实际经过的步骤、数据摘要、耗时与错误 |
| 业务流程图 | 给人读的业务过程和计算说明，可用 Mermaid |
| 模块清单与注册表 | 每个模块声明提供的接口、依赖及原因，启动时汇总 |
| 数据格式约定 | 接口和模块之间交换的数据及字段含义 |
| 存储模型与数据源适配 | 前者对应数据库，后者把外部平台数据转为业务数据 |

结构视图从代码生成，业务含义保留在文档，实际运行通过轨迹查看。三者共同说明系统，而不用各维护一套互相矛盾的描述。

## 2. 按业务划分模块

模块按一件能说清的业务划分，例如订单退款。模块主要表达规则和处理步骤，连接、记录、计时与错误转换等公共能力由框架提供。

本套框架用静态执行顺序图连接组件；组件各做一件事，调用顺序集中可见，简单模块可只有一个节点。执行器统一记录步骤、耗时和异常，业务组件保留明确失败，避免各自添加宽泛捕获。新流程需要并行、补偿或特殊保存顺序时，先确定业务含义，再增加对应结构。

模块清单声明业务用途、提供的接口、依赖的模块接口与原因。跨模块通过已声明的公开接口调用，依赖由框架提供；内部文件和存储实现留在本模块。启动与必要测试检查注册完整、依赖声明及引用有效，已有检查可用时直接复用。

同一业务规则由合适的模块维护。反复在多个入口补相似条件时，回头检查规则归属、依赖方向和保存范围；把原因修在能保证这条规则的位置。

## 3. 数据与保存规则

用 Pydantic 表达数据格式，字段说明业务含义，必要时补来源、单位和计算方法，让 OpenAPI 与数据字典能供人查阅。存储模型独立在数据访问层，业务通过仓储接口读写；外部来源经适配器转换，多平台按已有配置选择。

框架提供连接池、事务、分页、流式读取等共用能力；业务声明哪些修改一起成功或撤回、哪些可分批处理。权限和数据隔离也由业务说明，框架执行，不能从技术方便反推业务规则。未知规则用 business-rules。

默认记录节点输入输出摘要；解释不了已出现的问题时，再补有关字段并脱敏。数据记录为查明问题服务，范围、采样和保留期结合业务与存储成本确定。

## 4. 入口、版本与运行追踪

请求和响应有明确格式，错误包含错误码、种类、说明和请求编号；参数、资源不存在、业务和系统错误可区分。成功格式沿用项目约定，错误细节在运行记录中查看。

请求编号贯穿访问日志和业务步骤；异步任务与外部调用延续关联，让一次业务能查到它后续经过的地方。提供按 `trace_id` 或业务编号查询、导出的稳定入口，debug 可直接使用。

优先沿用已有记录方式。需要完整追踪平台时，可以采用 OpenTelemetry 及现成查看工具，再补业务步骤；说明接入、记录和日常维护成本。普通日志已能查清的问题使用现有能力。

接口版本仅有字段和格式差别时，在入口转换为统一业务数据；计费、退款或权限不同，先确定兼容规则，再安排业务规则选择。确认旧版本无人依赖后再移除。

大多数请求直接处理；耗时、需要重试或削减高峰的工作再进入队列。队列增加运维与排错成本，不会自动减少单个请求耗时。

## 5. 让系统可运行、可维护

统一处理输入校验、参数化查询、认证、权限执行、CORS、适用的限流、密钥读取和日志脱敏。配置集中读取并在启动时校验，`.env.example` 说明配置含义；缺必需配置时明确失败。

采用模块化单体，按实际环境提供部署与健康检查；Dockerfile 和 compose 示例随项目需要使用。状态放在数据库或缓存，业务与部署进程分开，性能检查按实际目标开展。

目录和名字用简单完整的英文说明用途，后端代码与业务文档分开。模块 README 说明业务用途、接口、依赖、处理流程和设计原因；可生成的结构信息来自清单。业务文档用一条具体操作开头，保留计算、字段、权限和保存规则，业务变化时一起更新。

项目入口由 project-agents-md 维护，架构信息尽量留在代码、测试和可生成视图中。[模板](references/templates.md) 按当前模块需要查用。

## 6. 迁移时保住已确认的行为

一次迁一个业务单元，先选能经过主要数据来源、计算、保存与接口的模块，检验框架是否支持真实业务。

1. 固定旧系统版本，协调迁移期间必要修复和客户急需改动；尚未迁移部分避免同时扩展功能。
2. 从旧系统准备请求和结果样例，明确动态字段比较办法。旧结果用于兼容比较，已知旧错误单独按确认规则处理。
3. 默认保留表结构、前端、接口路径与返回格式，差异在入口转换。确需改变时，明确数据迁移、兼容和恢复办法。
4. 在隔离数据上比较，新旧写入各从相同初始状态运行；付款、消息和通知用替代服务，避免真实副作用重复发生。
5. 按业务规则和数据格式完成模块、组件、执行顺序图与清单，再运行项目检查和对照样例，查看全部差异。
6. 部署、基本性能与兼容检查满足要求后，按已有授权切换这一模块；同一请求只由一套后端处理。

## 7. 取舍与检查

共享机制的选择用业务影响讨论：多维护什么、改动会影响谁、错误怎样发现与恢复。数据库、认证、队列、追踪存储、并行执行等重要选择先看已有决定，缺少答案时给推荐与代价，按全局第 8 节处理。

用 [质量检查](references/quality-checks.md) 选择本次适用项，保留项目必需检查。公共层变化覆盖实际受影响的模块，检查既包括结果，也包括规则归属、依赖和失败处理；完成程度按 pre-delivery-check 说明。
