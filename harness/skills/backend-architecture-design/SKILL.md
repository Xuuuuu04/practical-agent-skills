# 后端架构设计

## 1. 适用范围

为 FastAPI 单体后端安排框架、业务模块和旧系统迁移，使功能能按模块逐步增加，问题能通过运行记录定位。用户决定业务规则和重要取舍；你负责查证、提出设计建议、实现和检查。

由写代码的你直接参与架构讨论，让设计与实际实现保持一致。发现要求不完整或做法不合适时，用具体业务结果说明问题和建议；不要把自己的推断写成用户决定。

在已经基于这套框架搭好的项目里，以项目的 AGENTS.md、框架代码和测试为准，这份 Skill 提供原则和原因。框架的具体实现，比如成功响应是否加外层包装、用了哪个 ORM，以项目为准，不要按这份 Skill 去改框架。

影响业务正确、权限和模块依赖的重要规则，尽量由框架代码和已有检查保证，文档解释原因。先判断违规会造成什么错误，再决定是否增加测试；不把所有写作偏好、设计建议都做成检查，也不在已有检查之外重复实现同一条规则。

## 2. 目标和取舍顺序

1. 稳定可用。最坏的结果是看起来能用，一用就这里出错、那里出错。
2. 人能看懂、能审查。人看不懂就没法拍板，也不知道下一步该推进哪个模块。目录、命名、模块划分都服务于这一点：哪怕不太懂软件工程的人，打开目录也应该大致知道每部分是干什么的。
3. 易扩展、易修改。客户需求经常变，一次变更应该只影响少数模块。
4. 性能。要能承受相对较高的并发，但不能以牺牲前面几项为代价。

先满足权限、密钥与数据保护等最低安全要求，再在上面几项之间按顺序取舍；安全要求不因便利或速度而省略。每个机制都要说明解决哪个已经出现的问题，以及增加多少理解和维护成本；说不清用途就不增加。

框架基本成型后，只有真实业务或迁移需要才增加能力。模板说明一种可选实现，不要求一次配齐队列、缓存、轨迹平台和部署设施；先沿用项目已有能力，缺少的按当前目标补。当前方案已能满足目标和检查要求时，不再增加设计。

## 3. 痛点和框架的回应

| 痛点 | 原因 | 框架的回应 |
| --- | --- | --- |
| 客户需求模糊、经常变 | 没有模块化时，一处改动牵动很多地方，AI 修改时会加入大量防御性代码 | 按业务拆模块，模块之间只通过声明过的接口交互 |
| 修改时遗漏相关调用 | 代码分散，无法快速找到受影响的部分 | 控制模块范围，通过注册表找到相关模块，再检查实际调用 |
| AI 自下而上 debug，消耗大量 token | 运行时看不到数据在哪一步出错，只能逐层写临时测试、加打印 | 执行顺序图加运行轨迹：一次请求经过了哪些节点、每个节点的输入输出和耗时，都能直接查到 |
| AI 往一处堆代码，防御性代码和记录改动的注释冗余 | 模型有完整上下文，自己看得懂就不在乎组织；修错时习惯补一行注释、一个 TODO、一个备用分支 | 质量检查并入全量测试，文件过长、函数过长、重要业务说明缺失、残留 TODO、宽泛的异常捕获等确定问题会让检查失败；简单方法缺注释只提示人工判断 |
| 接口版本组织混乱 | 格式差异与业务差异混在同一层处理 | 格式转换留在接口层；计费、退款等业务差异按已确认的兼容规则处理 |
| 时间长了没人记得业务 | 代码几十万行，两三个人维护，甲方响应慢，出了问题只能现场让 AI 读代码 | 业务文档记录流程、计算规则和字段含义，每次改业务同步更新 |
| 不同模型风格各异 | 有的模型啰嗦，有的写得乱 | 重要规则由代码和检查保证，表达与设计建议结合实际判断 |

## 4. 先分清几组概念

设计和讨论时区分下面几组概念。名称相同却含义不同时，用具体输入、输出和使用位置说明差别。

"图"有三种。执行顺序图是写在代码里的静态定义，说明一个模块由哪些组件组成、按什么顺序和条件执行。运行轨迹是某一次请求实际经过了哪些节点、每个节点的输入输出、耗时和错误，属于运行时数据。业务流程图是业务文档里给人看的流程和计算说明，用 Mermaid 写。三者的关系是：执行顺序图是模块结构的唯一来源；业务文档里描述结构的部分可以由执行顺序图生成，业务含义由人来写；运行轨迹挂在执行顺序图的节点上。这样三者不会各说各话。

"注册"有两种。模块清单是每个模块声明自己对外提供哪些接口、依赖哪些其他模块的哪些接口，框架启动时汇总成全局注册表。组件登记是模块内部把组件登记进本模块的执行顺序图。

"数据"有三种。数据格式约定是在接口上、模块之间流转的数据结构，每个字段带业务含义说明。存储模型是数据库表对应的模型，只在数据访问层内部使用。数据源适配是外部平台（SaaS、第三方接口）的数据进入系统时的转换层。把三者分开，使业务数据的含义不随来源平台或数据库结构改变。

"中间件"有两种。请求中间件是 FastAPI 处理请求过程中的一环，比如请求 ID、访问日志、异常处理、限流。基础设施组件是数据库、缓存、消息队列、对象存储这些外部服务，框架提供统一的接入方式，业务模块不直接连接它们。

## 5. 设计规则

### 5.1 入口层

错误响应使用统一的结构，至少包含错误码、错误种类、说明和请求编号；错误码集中定义，参数校验错误、找不到资源（404）、业务错误、系统错误各有明确的码和提示。原因：前端和 AI 都能按固定格式处理；排查时凭请求编号就能找到这次请求的运行轨迹。成功响应是否加统一的外层包装，由项目决定并写进项目 AGENTS.md；迁移旧系统时，以旧接口的格式为准。

每个请求生成请求 ID，贯穿访问日志和运行轨迹。所有请求都有访问日志，生产环境可以查。

接口的请求和响应都使用数据格式约定。FastAPI 自动生成的 OpenAPI 文档因此带上字段含义，接口文档一导出就能用。

大多数请求同步处理。消息队列用在耗时任务、削峰、需要重试的异步工作上，不放在所有请求前面。原因：队列不会让单个请求变快，它的作用是把工作移出请求过程；让每个请求都过队列，会增加延迟、部署负担和排查难度，中小企业的负载通常用不上。提高并发主要靠异步 IO、多个 worker 进程、连接池和缓存。

### 5.2 模块层

按业务功能拆模块，以一个人能说清用途、看懂主要处理过程为标准，比如订单退款。组件较多时先看是否包含多个独立业务，不按数字硬拆。

模块内部由组件和执行顺序图组成。每个组件只做一件事，组件之间不直接互相调用，由执行顺序图把它们串起来。原因：组件互相调用时，依赖关系要读完代码才知道；执行顺序图把顺序和条件集中写在一处，人和 AI 都能一眼看懂。

执行顺序图的执行器就是这个框架里的"类 AOP 层"。执行器调用每个组件时，统一记录运行轨迹、计时、把异常转换成统一的错误结构；组件内部不写这些代码，也就不需要自己加防御性的异常处理。

执行顺序图保持静态、声明式，只支持顺序、条件分支等少数几种结构，不允许在运行时动态拼装。原因：动态拼出来的图无法事先审查，运行轨迹也对不上结构。简单的模块允许只有一个节点，不要为了形式硬拆组件。

每个模块有一份模块清单，写明模块名称、业务用途、对外接口、依赖的其他模块接口及依赖原因。框架启动时和测试时都检查：没有注册的模块、调用了清单里没声明的依赖，都会报错。

跨模块调用只通过对方清单里声明的接口（Python 的 Protocol 或抽象类），实现由依赖注入提供；不允许导入其他模块的内部文件。这一条用 import-linter 这类工具写成测试。原因：如果注册表变成"想要什么就去取什么"的地方，依赖关系又会藏进代码里；依赖在清单里声明，人才能从注册表看出谁调用了谁、谁被调用得多。

模块主要写业务。工厂、适配器、依赖注入这些模式由框架提供，模块照着用；模块内部只在需要时用小的优化手段，比如缓存、批量处理。

### 5.3 数据层

数据格式约定用 Pydantic 定义，每个字段都写业务含义说明，需要时写来源、单位和计算方式。说明进入 OpenAPI 文档，并用于导出数据字典，使修改时能查明字段含义。没有说明的字段会让质量检查失败。

存储模型和数据格式约定分开。数据访问通过仓储接口，业务模块不直接写 SQL，也不直接操作 ORM 会话。原因：换数据库、改表结构时，影响只到数据访问层。

外部数据源通过适配器接入，适配器负责把外部格式转换成数据格式约定。同一类数据有多个来源平台时，用工厂按配置选择适配器。原因：客户换平台或接入新平台时，只需要增加一个适配器。

框架提供连接池、事务、分页或流式读取和内存限制的通用能力。业务模块仍要声明哪些修改一起成功或撤回、哪些数据可以分批处理；框架执行这些规则，不能替业务决定。比如订单创建和库存扣减是否一起成功，要由订单业务规则确定。

需要解释字段的计算过程时，先根据组件的输入输出说明哪个组件产出了哪些字段，再用本次请求的运行记录查实际数据。默认记录节点摘要；只有摘要无法解释已出现的问题时，才增加有关字段的记录，并处理敏感信息。

### 5.4 运行轨迹

每个请求记录经过的执行顺序图节点、每个节点的开始和结束时间、输入输出摘要、错误信息，可以按 `trace_id` 查询。提供一条命令或一个接口，按 `trace_id` 导出一次请求的完整轨迹，AI debug 时直接读取，不需要写临时脚本。

底层建议采用 OpenTelemetry 标准记录，在它上面提供按业务节点查看的视图。原因：OpenTelemetry 已经能自动记录 FastAPI、数据库、HTTP 客户端的调用，自己发明格式需要长期维护，也接不进现有的查看工具。

输入输出里可能有个人信息和敏感数据，记录前要脱敏；生产环境按比例采样记录完整数据，出错的请求全部记录；轨迹数据设置保留期限。原因：全量记录每个字段会带来泄露风险和存储成本。

### 5.5 接口版本

只有字段名称、结构等格式差异的版本，转换放在接口层：每个版本有自己的请求和响应格式约定，以及转换成业务核心数据格式的代码。业务核心只有一份实现，模块内部不出现按版本判断的分支。新旧版本的计费、退款或权限规则不同时，先明确兼容要求，再设计业务规则的选择方式，不把业务判断藏进格式转换。旧版本停止维护后，确认无人依赖再删除对应内容。

### 5.6 安全

框架层统一处理：输入校验（数据格式约定）、参数化查询（仓储层）、认证与权限（依赖注入）、CORS、限流、密钥只从环境变量或密钥服务读取、日志和运行轨迹脱敏、错误响应不暴露内部细节。框架处理通用安全措施；业务模块声明具体权限和数据隔离规则，业务文档记录谁能看、能改哪些数据。例如客服可查看退款进度，但能否读取收款账户要由业务规则决定。

### 5.7 部署和运维

`.env.example` 列出配置项及含义。配置统一读取并在启动时校验，缺少必需配置就拒绝启动。提供当前环境需要的部署、环境检查和健康检查；有性能目标或容量问题时再做负载检查，已有工具可用时不重复写脚本。

为 Docker 化留好位置：提供 Dockerfile 和 docker-compose 示例；服务本身不保存状态，状态放在数据库和缓存里，为多实例和弹性扩容留出条件。

坚持单体。原因：中小企业客户负担不起微服务的运维成本；模块化的单体在确实需要时，也能把某个模块单独拆出去。

### 5.8 命名和目录

用最简单的英文单词，包名要完整说明用途，比如 `order_refund_calculation`，不要写成 `orc` 或 `calc`，也不用生僻词。每一层目录的信息量要低：打开任何一层，只懂一点英文的人也能大致知道每个文件夹是干什么的。

项目顶层把后端代码和业务文档分开放，具体目录名以项目为准。

## 6. 质量检查

运行适用于当前改动的质量、功能和集成检查；修改框架公共部分时，覆盖实际受影响的模块。项目要求的完整检查仍要完成，不因改动小而跳过。能确定违反规则的项目检查失败；注释、用词和设计是否合适，由当前 Agent 判断。具体检查项见 `references/quality-checks.md`，范围与完成条件按 pre-delivery-check Skill。

每条失败信息写清哪个文件、违反哪条规则、原因和处理办法，使检查结果可以直接用于定位和修改。详细清单和建议阈值见 `references/quality-checks.md`。

## 7. 文档

项目根目录放 `AGENTS.md`，按 project-agents-md Skill 的固定格式写：运行命令、目录地图、去哪里找、数据怎么流动、不要做的事和原因。AI 了解一个项目时，通常先列目录，再读各文件夹下的 README 和 `.md` 文件，所以这些文件要写清楚为什么这样设计，只写要怎样做是不够的。

每个模块有 README，固定几节：业务用途、对外接口、依赖、处理流程、为什么这样设计。README 有行数上限，超过就压缩整理。接口列表和依赖这类结构信息尽量从模块清单生成，避免手写内容和代码不一致。

`docs/` 下放业务文档，只写业务：用中文自然语言和 Mermaid 写清流程、计算规则、字段含义、功能给谁用、为什么这样做。不写凭空编造的性能指标，这类数字要等系统用起来才知道；框架已经解决的安全等通用问题也不写。每次改业务，同步修改业务文档。

不写单独的架构文档。架构由代码和测试保证，结构视图从注册表生成。

模块目录、模块清单、执行顺序图、数据格式约定、README 和业务文档的模板见 `references/templates.md`；根目录 `AGENTS.md` 的格式以 project-agents-md Skill 为准。

## 8. 需要用户决定的设计问题

下面这些问题，在新项目有实际需要时提出；无需队列等能力时不为了选型先引入。由 Agent 查现有环境、比较并给推荐，说明部署成本、日常维护和业务影响；用户决定这些影响是否接受，不只给一串技术名称让用户盲选。先看项目 AGENTS.md 和 `.agent/decisions.md`，已经定下的不要再提；还没定的，整理出选项、各自的代价和你的建议，交给用户决定，不要自己定下来写进框架。

1. 任务队列：基于 Redis 的轻量方案（ARQ、Dramatiq、Celery 等），还是 RabbitMQ、Kafka（Python 里可以用 aio-pika、aiokafka）。对中小企业的单体服务，建议先用 Redis 方案。
2. 运行轨迹的存储和查看：接入 Jaeger、Grafana Tempo、SigNoz 这类现成工具，还是存进数据库、自己做一个管理页面。
3. 执行顺序图支持哪些结构：是否需要并行执行，事务怎样和节点对应，失败后是否需要补偿操作。
4. ORM 和数据库：SQLAlchemy 2.0 异步加 Alembic，还是 SQLModel；PostgreSQL 还是 MySQL。
5. 质量检查的具体阈值：文件行数、函数行数、复杂度、README 行数。
6. 认证方案。
7. 基础设施组件的版本由框架统一锁定，还是由使用者自己提供。

## 9. 工作方式

动手前先读项目根目录的 `AGENTS.md`、全局注册表、相关模块的 README 和业务文档。

修改框架层之前说明用途、原因和受影响模块。已有明确方案和授权时继续执行；新增重要设计选择或改变未确定的业务行为时，按全局规范第 8 节等待决定，不对同一方案重复确认。框架层影响多个业务，检查范围覆盖实际受影响的模块。

设计新机制时，先判断它能否达到用户目标，比现有做法多解决什么、增加什么成本，再给推荐。用户指定了方法，也要检查是否合适；已经满足目标时，建议结束，不继续寻找可加的能力。

用户描述某个机制时如果比较模糊，用一个小例子说明不同理解的结果。是否需要等待统一按全局规范第 8 节判断，不因措辞模糊就暂停所有工作，也不替用户决定未确定的业务含义。

## 10. 把旧系统迁移进框架

"迁完"的标准是新系统符合已确认的兼容规则，代码写完只是开始。按全局规范第 6 节，用旧系统输出检查行为是否保持不变，不能因此证明旧计算正确；已知旧错误按确认后的处理办法比较。

1. 固定旧系统的版本。迁移期间，旧系统里还没迁的模块只修 bug 和客户急需的改动，不再加新功能。客户要改的正好是某个待迁模块时，可以先迁这个模块，再在新系统里改。
2. 一次迁一个业务单元。第一个模块要选能走通项目主要数据来源的那条路（例如外部采集、入库、计算、接口），让它检验框架里还没被真实业务用过的部分。
3. 把旧系统作为默认的兼容对照。迁每个模块之前，先从旧系统录下一批真实请求和返回结果，存成对照样例；新模块跑同样的请求，用程序逐个字段对比，记录差异；已知旧错误不直接复制，由用户决定本次保留还是修正。动态时间、随机编号等字段先确定比较规则，不逐字比较。迁完要求符合已确认的兼容规则，新增错误已处理。
4. 默认先保持表结构，避免代码与表结构同时变化。对照在隔离的数据副本上进行，写入请求各自从相同初始数据运行，消息、付款和通知等外部操作使用替代服务，不能向真实系统执行两次。上线切换时同一请求只由一套后端处理；迁移确实需要改表时，单独提出数据迁移和回退办法。
5. 前端不改。已迁移模块保持旧系统的接口路径和返回格式，把旧格式当作接口层的一个版本，只在接口层做转换，业务核心只有一份。
6. 对照全部通过后，只把这一个模块的请求切到新后端。切之前确认部署能跑通，并做一次基本的性能对比。
7. 每个模块按"先写业务文档和数据格式约定，再拆组件、写执行顺序图和模块清单，最后跑项目要求的测试和对照样例"的顺序做。不要一次搬一大片代码进来。

## 11. 评审时问的问题

- 这个模块能不能用一两句话说清楚它负责什么？说不清，通常是拆得不对。
- 从模块清单能不能看出它依赖谁、被谁依赖？代码里有没有绕过清单的调用？
- 组件之间有没有直接互相调用？
- 数据格式约定的每个字段都有说明吗？说明写的是业务含义，还是只把字段名翻译了一遍？
- 出了错，能不能凭 `trace_id` 看到出错的节点和它的输入？
- 有没有为假设的将来需求加的抽象、配置或备用分支？
- 新增的接口版本有没有让模块内部出现版本分支？
- 业务文档有没有跟着改？
