# 质量检查

按当前改动和实际影响选择检查，项目要求的完整检查仍要完成。下面是本框架可用的检查项，不是每次都要新增的检查工具；已有检查能证明的，不另写一套。确定违反适用规则的检查项失败时，测试不通过；涉及含义的提示人工判断，完成条件按 pre-delivery-check Skill。

## 失败信息的写法

下面是程序检查记录的写法，保留文件、行号、规则、原因和处理办法。跟用户反馈时先说它影响哪件事，详情需要时再给，不照着日志逐条念。例如：

```
server/modules/order_refund_calculation/components/calculate_refund_amount.py:48
函数 calculate_refund_amount 有 72 行，上限是 60 行。
原因：过长的函数人很难审查，也是把逻辑堆在一起的典型表现。
改法：按实际业务步骤拆分；独立业务步骤可放入组件，局部辅助计算可留在同一文件，不为了行数增加无用途的文件。
```

## 检查项

文件、函数、文档的长度上限沿用 pre-delivery-check 脚本的默认值；其余阈值是建议值，采用前按项目的明确约定和实际维护成本判断。

| 检查项 | 为什么 | 建议实现 | 建议阈值 |
| --- | --- | --- | --- |
| 文件长度 | 过大的文件难审查 | 自写脚本统计行数 | 沿用 pre-delivery-check 的文件上限 |
| 函数长度和复杂度 | 很长的算法块难以理解 | ruff 的 C901、PLR0912、PLR0915，加自写的函数行数检查 | 函数长度沿用 pre-delivery-check 的上限，圈复杂度 10 |
| 命名规范 | 统一风格，便于人理解 | ruff 的 N 系列规则 | 按 PEP 8 |
| 命名用词 | 避免生僻词和过度缩写 | 沿用项目命名规则，提示后人工检查业务含义，不另设词典检查 | 简单、完整、含义明确 |
| 残留 TODO、FIXME | AI 修错时留下的标记没人处理 | ruff 的 FIX、TD 系列规则 | 不允许 |
| 注释掉的代码 | 让人分不清哪些代码有效 | ruff 的 ERA001 | 不允许 |
| 缺少注释 | 不读代码的人靠注释上手项目，AI 常常只留下自己看得懂的代码 | 自写脚本：检查业务入口、类和关键计算的说明；change_health.py 提示后人工判断 | 有业务含义，简单方法不重复翻译 |
| 宽泛的异常捕获 | 典型的防御性代码，会把真正的错误藏起来；异常应该交给执行顺序图的执行器统一处理 | ruff 的 E722、BLE001、S110；业务模块目录内禁止 `except Exception` | 业务模块内不允许 |
| 数据格式约定字段说明 | 字段含义不能靠 AI 推断 | 自写测试：遍历所有数据格式约定，检查每个字段都有 description | 全部必须有 |
| 模块注册完整 | 未注册的模块在注册表里看不到 | 自写测试：每个模块目录都有模块清单并出现在注册表里；执行顺序图引用的组件都存在；没有组件游离在执行顺序图之外 | 全部必须满足 |
| 跨模块依赖 | 绕过清单的调用会让依赖关系重新藏起来 | import-linter：模块之间只能导入对方的接口文件；框架层不能导入业务模块 | 全部必须满足 |
| 组件之间直接调用 | 组件应该由执行顺序图串联 | import-linter：同一模块内的组件文件之间不能互相导入 | 全部必须满足 |
| 模块 README | 目录里的说明是 AI 了解项目的第一入口 | 自写测试：README 存在、包含固定小节、不超过行数上限 | 150 行 |
| 其他文档长度 | 文档太长就没人看，AI 读起来也耗 token | 自写脚本 | 沿用 pre-delivery-check 的文档上限 |
| 业务文档同步 | 业务改了文档没改，以后就没人说得清 | 自写测试：每个模块在业务文档里有对应章节；模块清单或数据格式约定改了、业务文档没改时给出提醒 | 缺少章节算失败；未同步先作为提醒 |
| 类型检查 | 数据格式约定在模块间流转，类型错误要尽早发现 | mypy 或 pyright | 业务模块全部通过 |
| 测试规范 | 测试也要统一，否则每个模型各写各的 | 自写测试：重要业务规则有功能测试，真实 bug 有针对性测试，命名和位置统一 | 全部必须满足 |

## 使用时注意

机械检查只确定能由程序判断的事；注释是否有用、用词是否属于技术或业务含义，提示后人工判断。设计与业务结果按规则、样例和实际数据检查，不能用格式通过代替。

阈值定得太严，模型会为了通过检查把代码拆得支离破碎，比如拆出很多只有两三行的函数；定得太松又起不到作用。先用建议值跑一段时间，再根据实际情况调整。

误报或确有业务原因需要例外时写明范围、原因和检查办法，不为通过检查放宽整包规则。会影响业务结果或保护措施的例外按全局规范第 8 节处理。
