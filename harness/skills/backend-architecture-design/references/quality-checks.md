# 质量检查

按实际影响选项，复用已有工具。本表用于本套框架；确定违反已采用的规则才算失败，含义与结构提示人工判断。

| 检查项 | 判断与可用工具 |
| --- | --- |
| 长度与复杂度 | 长度提示沿用 pre-delivery-check；复杂度可用 ruff C901、PLR0912、PLR0915，圈复杂度 10 为建议值 |
| 命名与注释 | 按项目命名规则检查业务含义；类、入口和关键计算说明用途，简单名字不重复翻译 |
| TODO、FIXME 与旧代码 | 处理未完成标记，删除注释掉的旧实现；可用 ruff FIX、TD、ERA001 |
| 异常处理 | 失败仍可发现；记录后抛出或明确转换可保留，业务模块避免重复承担入口错误处理；可用 E722、BLE001、S110 提示 |
| 数据格式 | 字段有业务说明，来源、单位和计算规则按需补充 |
| 注册与引用 | 模块清单、组件引用和执行顺序图完整有效 |
| 跨模块依赖 | 只调用公开接口，框架不依赖业务模块；可用 import-linter |
| 组件调用 | 本框架的调用顺序在执行顺序图定义，组件不直接互调 |
| 模块 README | 业务、接口、依赖、流程与设计入口齐全，150 行为建议长度 |
| 业务文档 | 重要规则有对应说明，业务变化更新文档；结构变化只触发有关提醒 |
| 类型与测试 | mypy 或 pyright 检查类型；测试覆盖重要规则与真实 bug |

检查记录给文件、行号、规则、原因与处理办法。例如：

```text
calculate_refund_amount.py:48：函数 72 行，超过默认提示值 60。
检查能否按独立业务步骤拆分；连续计算有合理原因时保留，不增加无用途的函数。
```

项目明确限制优先。例外说明范围、原因和检查办法，不为通过检查放松整包规则。
