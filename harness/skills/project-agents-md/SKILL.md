# 维护项目级 AGENTS.md

## 1. 为什么要维护它

项目级 AGENTS.md 是项目入口，让 Agent 知道怎样运行、去哪里查、哪些约定容易误解。信息多不等于有用；先判断读者做什么需要它，只保留每次都用得上的入口和不容易查到的说明，详情指向现有文档。

## 2. 固定格式

小节标题固定用下面这些，不增不减。某一节暂时没有内容，就写"暂无"。

````markdown
# 项目名

## 这个项目是什么
两三句话：业务是什么、给谁用、现在处于什么阶段（开发中、已上线、迁移中）。

## 怎么运行
- 安装依赖：`命令`
- 启动：`命令`
- 测试：`命令`
- 质量检查：`命令`
- 数据库迁移：`命令`

## 目录地图
- `路径/`：一句话说用途
写到第二层，重要的目录写到第三层，并标出入口文件。

## 去哪里找
- 接口定义：`路径`
- 业务规则和计算：`路径`
- 数据模型和字段含义：`路径`
- 配置和环境变量：`路径`
- 运行记录和排查工具：`命令或路径`
- 业务文档：`路径`

## 数据怎么流动
一小段话：数据从哪里来，经过哪几层，到哪里去。

## 本项目的约定
只写和全局规则不同、或者全局规则没有覆盖的部分。

## 不要做的事
- 事情。原因：……

## 已知的坑
- 以前真实遇到过、下次还会遇到的问题，一条一句，写清楚怎么避开。
````

"去哪里找"是最能减少搜索的一节：Agent 最常花 token 的地方，就是找"接口在哪定义""这个字段在哪计算"。每一项都写到具体的文件或目录。

## 3. 不写什么

- 改动记录、更新日期、"本次修改了……"：历史交给 git，任务进度写在 `.agent/` 里。
- 能从代码里几秒钟看出来的内容，比如函数列表、每个文件的说明。
- 全局 AGENTS.md 已经写过的通用规则，包括中文词表、等待条件和完整交付格式；需要提醒时指向原位置，不复制一份。任务检查步骤引用对应 Skill，项目只写实际命令和明确的特殊要求。
- 还没确认的计划和猜测。

## 4. 什么时候更新

- 新增、删除、移动了目录或模块：更新"目录地图"和"去哪里找"。
- 运行、测试、部署的命令变了：先实际跑通，再更新"怎么运行"。
- 用户明确确认了一条长期项目约定：更新"本项目的约定"，说明内容和原因。建议、临时假设和没有被反对的选择不写成用户决定；新要求替代旧规则时原位置改写。
- 发现一个下次还会遇到的坑，或者用户纠正了一个会反复出现的错误：更新"已知的坑"或"不要做的事"。
- 一次普通的功能修改或 bug 修复，通常不需要更新。

## 5. 怎么更新

1. 先读完整个文件。
2. 只改受影响的小节，在原位置改写；过时的内容直接删掉或替换，不在后面追加"更新"。
3. 小节标题保持不变。内容放不下时，先压缩已有内容。
4. 改完运行检查脚本，按提示修正：

   `python <本 Skill 所在目录>/scripts/check_agents_md.py <项目根目录>`

   它会检查行数是否超过上限、固定小节是否齐全、文中用反引号写到的路径是否存在、有没有日志式的写法。脚本只读文件，不修改任何东西。
5. 在交付说明里用一句话说明改了哪一节。

## 6. 第一次创建

1. 运行下面的脚本，得到目录结构和每个目录的文件数、行数：

   `python <本 Skill 所在目录>/scripts/dir_overview.py <项目根目录>`

   每个目录的用途，要读过其中的代码或 README 再写，不要按目录名猜。
2. 找到启动和测试命令，运行适用且安全的命令；缺少服务或会写真实数据时，说明尚未验证的原因，不为写说明新建测试或启动无关服务。
3. 能确定的小节先写；没有相关内容的写"暂无"，待确认的明确写出缺什么，不把未知写成不存在；只询问影响业务结果或运行方式的问题。
4. 检查文件中的事实、命令和路径；只有影响业务或重要代价的未定问题，按全局第 8 节等待。已授权维护说明时直接完成，不另加整份文档的批准步骤。

## 7. 长度

全文不超过 150 行。超过时，优先压缩"目录地图"（只保留第二层），再删掉"已知的坑"里已经修好、不会再出现的条目。

## 8. 各工具怎么读到它

读取入口以本机实测为准。Claude Code 通过 CLAUDE.md 的 `@AGENTS.md` 导入项目说明，保留原有内容；其他工具检查是否实际读取根目录 AGENTS.md。安装检查问路径和原文，行为检查看具体场景下做了什么，不能只靠模型自述判断生效。
