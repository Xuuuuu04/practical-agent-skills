# 排错与修复

## 1. 确定错误

用一条实际业务列出输入、操作、应得结果和实际结果，记录环境、版本、触发条件与影响。预期不明确先用 business-rules。

生产故障仍在扩大时，按已有授权回退或暂停相关工作，保留排查证据；临时恢复与原因修复分别处理。

## 2. 找首次出错的位置

看本次有关的入口、处理步骤、保存与外部调用，拿同一请求或业务编号的实际数据逐段比较。找到正常与异常的交界，确定哪条规则本应保证正确。

优先用已有日志、trace、测试和查询入口。证据不足时补能区分当前解释的最少记录或最小复现，每次尝试说明验证什么、排除了什么；重复失败按全局第 4 节换办法。

## 3. 在原因所在处修复

| 原因 | 修法 |
| --- | --- |
| 局部实现违反明确规则 | 修正该规则所在处 |
| 多入口重复实现或共用函数出错 | 集中规则或修共用函数，覆盖受影响入口 |
| 多层补救、保存范围或依赖安排导致重复错误 | 说明结构原因、影响和代价，结合架构 Skill 调整 |
| 流程缺少定位能力 | 关联请求、后台任务与外部调用，提供稳定查询入口 |

只把已证明属于同一原因的问题合并处理。修法消除错误条件，不在结果末端叠补丁；共用修复使旧补救失去用途时删除旧补救。

补充运行记录时保留关键步骤、耗时、结果和错误，必要数据脱敏。先复用现有工具，新追踪平台说明部署与记录成本。

## 4. 验证修复

重现原触发条件，比较应得与实际结果，再查相关正常情况和受影响入口。并发、重试、部分失败只在与原因有关时覆盖。

用 pre-delivery-check 查看最终差异，交付说明原因、修法、结果及未处理的数据或环境。
