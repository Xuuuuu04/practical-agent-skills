# 排错与修复

一次好修复，会让错误产生的条件更少，也让下次出错更容易查清。关心整个项目怎样运转：报错消失以后，业务结果、数据关系和代码结构都值得再看一眼。

## 1. 先认清发生了什么

读项目说明、相关业务规则和已有运行记录，用一条具体业务说清：什么输入、经过什么操作、应得什么、实际得到什么。记录版本、环境、触发条件和影响范围；用户猜测与报错位置是线索，原因还要查证。应得结果不明确时用 business-rules。

生产故障先判断是否仍在扩大影响，按已有授权采取回退、暂停相关任务等恢复办法。临时恢复和原因修复分别说明，保留能继续查明原因的证据。

## 2. 顺着实际数据定位

先看相关部分的结构，弄清数据从入口经过哪些业务步骤、在哪里读取和保存、会调用哪些外部服务。只画本次需要的一小段，随后拿同一请求或业务记录的实际数据与它比较。

从正常和异常交界的地方找起：上一步输出是否正确，下一步从哪里开始偏离，哪一层本应保证这件事。按已有证据缩小范围；流程长时逐段比较，不从上到下盲读所有文件，也不在看到异常的末端直接补条件。

优先用已有日志、trace、测试和查询入口。记录不够时，先说缺哪项证据，再加能区分当前几个解释的最少记录或最小复现。一次尝试说明想验证什么，结果排除了什么；没有新信息就换办法，时间与重复失败的处理沿用全局第 4 节。

## 3. 判断该修在哪里

把原因说成能检查的因果关系：哪个条件触发、哪个步骤处理错、为何造成当前结果。区分已经证实、仍在怀疑和暂未复现的部分。

| 查到的情况 | 修复方向 |
| --- | --- |
| 一处实现违反已明确的规则 | 在应负责该规则的位置修正，保留其他正常行为 |
| 多个入口重复实现同一规则，错误来自同一个缺陷 | 修正共用处或集中这条规则，检查实际受影响的入口 |
| 多层相互补救、保存范围不清、依赖混乱导致同类错误反复发生 | 提出具体的结构调整，说明现有安排为什么容易出错、调整影响谁、怎样验证 |
| 数据经过许多步骤，每次出错都得临时写脚本猜 | 补充可重复使用的定位能力，先利用现有请求号和业务号，再考虑完整运行追踪 |

比较修法时看四件事：能否消除原因，放置位置是否合理，是否减少同类错误，后续理解和维护要付出什么。改得少不自动代表合适，改得多也不代表深入。已查明且属于任务范围的修复直接推进；重要结构取舍和未定业务按全局第 8 节处理，后端结构用 backend-architecture-design。

连带检查围绕同一原因展开，说明哪些已有问题确实相关。旁边另一个现象先保留为线索，证明有关再合并处理。Goal 持续执行时也保留这个判断，每次改动都能解释它消除了什么原因。

## 4. 让下次容易查

需要运行追踪时，让同一次操作的请求、后台任务和外部调用能关联起来，留下关键步骤、耗时、结果、错误及必要数据摘要。优先复用项目已有 trace 工具；新平台的部署、记录开销和保留方式说清楚，再按项目安排实施。

给出一个稳定入口，能按 `trace_id` 或业务编号查到这次操作。日志里的敏感字段脱敏，记录量按定位需要选择。一处普通错误可用现有日志解决时，就使用现有能力。

一次性排查材料按全局第 5 节放临时目录并清理；反复需要的查询或复现工具进入项目已有工具目录。目录和查询方式变化时，用 project-agents-md 更新入口。

## 5. 证明原因已经消除

用原触发条件验证修复，再看受同一原因影响的入口及相关正常情况。预期来自已确认业务，真实 bug 留下可重复测试；并发、重试、部分失败等情况在与原因相关时验证。

按 pre-delivery-check 查看实际差异：是否在正确位置处理，是否留下重复补丁、掩盖失败、绕过模块接口或多余临时文件。已经修正共用原因的，删除因此失去用途的局部补救。

交付用具体业务说清原因、修法、验证结果，以及尚未处理的数据或运行环境。临时恢复、代码修好、检查通过和生产恢复各说实际状态；仍未查明时交付证据和下一项检查，不把猜测报成修复。
